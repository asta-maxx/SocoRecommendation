A. Blocking

1. The ml_-scoped write credential — Aravinth

Ask: a database user that can write only collections prefixed ml_, and nothing else. The application credential stays read-only.

Where it stands: the read-only credential is confirmed correct — readonly_user holds role SocoReadonly, which grants find, listCollections, listIndexes, collStats, dbStats, changeStream, killCursors, planCacheRead on soco. No insert, no update, no remove. That half is done.

The write credential does not exist. The engine currently authenticates with a user holding atlasAdmin — full access to every database — which is the opposite of the requirement.

Why it matters: the Python side refuses to write outside ml_ and 13 tests hold that. But a guard in the client is a guard a future client might not have. The requirement is a guard in the database.

The db.createRole / db.createUser commands are written out in HANDOFF.md section 3. Please also confirm the scoping actually holds — that the user can write ml_user_interest_scores and cannot write users, posts, postevents or orders.

Related: ml_ must live in the same database as the application data (Q14 Option A — the app runs one MongoDB connection and there is no second database). During the build it is on a separate cluster, so nothing has yet been proven against the real deployment shape.

9. The uniqueness key

DS-015 says "one document per user per category". Task 15 says Method B "writes under its own method value so both methods coexist in one store". Those reconcile only as user_id + category + method.

Built as: user_id + category + method + model_version — that triple plus the model version.

Same version re-run New version
Triple only overwrites overwrites — previous generation lost
With model_version overwrites accumulates a new generation

Why: a parameter change should not destroy the evidence of what the previous configuration produced.

Cost: the store grows per version, and the display script must filter on model_version or it shows every generation at once.

Kala, 10 September: keep model_version.

Settled. The key is user_id + category + method + model_version, as built. The display script must filter on model_version so it shows one generation at a time.

10. categories is plural and an array — ✅

The task list says category, singular. It has to be plural.

A post carrying several categories contributes full weight to each, not a divided share — that is U03's entire purpose, and U03 is a narrated demo user. A singular field cannot express it, so the generator would need a second code path just for U03 — a special case built to make a demonstration work, which is a finding rather than a shortcut.

The array holds one element in the ordinary case, so plural costs nothing.

Kala, 10 September: correct — the generator uses categories.

12. A reversal is an event_type, not a flag — ✅

D. Smaller things, for the record

BSON dates carry milliseconds, not microseconds. A timestamp written and read back is not equal to the one that went in. Irrelevant to decay at day scale, but it will break any conformance test that compares timestamps exactly.

posts.userId holds both ObjectId and String. Any join on it must match both forms; a $lookup matches one type and returns a partial result — which is worse than an empty one, because it looks like the query worked. Handled, but worth knowing before anyone writes an aggregation.

session_id is fv_<postId>_<ts> — one per view, not per session. It cannot be used to group a user's activity.

Credentials in logs. A connection string reached a test traceback during the build. Both URIs are now marked so they cannot be printed, and a test enforces it. The exposed Atlas password should still be rotated.
