=== SHEET: Home
SOCO Recommendation Engine: Wave 1A build list
Issued by Kala, Cristo Labs. Version 1.3, 29 September 2026: replaces version 1.2 of 28 September. What changed, and when, is on the sheet 'Change register'. Owners update only the Status column.
What this is | Every item that must be built for Wave 1A, for the app, the database and the engine: 69 items (24 app, 16 database, 29 engine). Each item says what to build, who builds it, what it waits on, and how to check it is done. Everything needed is written in the item itself. / In v1.3, 14 app and database items are marked Not needed: the engine adapts to what the platform already has. ENG-01 to ENG-04 are built and unchanged; the adaptations that touch them are in ENG-29.
What Wave 1A delivers | Recommendations a shopper sees in two places: the For You feed, and product detail and cart. Promoter scores feed the ranking but are not shown. Opportunity scores are computed and not shown. Fraud is detected and reviewed by a person; nothing is applied automatically. Brand and campaign matching is not in Wave 1A. / Wave 1A delivers a working, tested engine and the tracking it needs to learn. Recommendation quality depends on real user traffic, which does not exist yet, so the first weeks will look close to recent and popular.
The values in here | Every number on the Settings sheet is a starting choice made on sound practice and on what the SOCO data shows today. None of them is proven on SOCO traffic yet. The Settings sheet says what each value changes with, and when.
Who builds what | Aravinth: the app (Flutter), SOCO_BE, the admin panel and the platform database. The IDs start with APP and DB. / Allen: the recommendation engine. The IDs start with ENG.
How to use it | 1. Open 'Build list'. Filter the Owner column to your name. / 2. Work in step order. / 3. Before starting an item, check its 'Waits on' column. If the other person's item is not done, open 'Waits on the other team' and ask them for it directly, quoting both IDs. / 4. When an item is done, run 'How to check it is done'. Save the result as a file named <item ID>_<date> in the shared project folder 'Wave1A checks' (Sanjai to create folder and give access). Nobody approves it: a pass means done. / Owners update only the Status column of their own items, using the list below. Nothing else in the workbook changes. Every go-live, switch-off and setting change follows a written rule here. None needs anyone's approval.
Order of work | The work runs in six steps. Start the next as soon as its items are done: nothing waits for a calendar date. / Step 1 – within 7 working days of starting: data retention, access, foundations, and the first app and database fields. / Step 2 – within 12 working days: the event path, order events, M1 on live data, and the engine serving core. / Step 3 – within 17 working days: retrieval, product ranker, promoter score, and the app calling the engine. / Step 4 – within 22 working days: ranking, fraud, opportunity ordering, and the checks. / Step 5 – within 27 working days: acceptance checks and monitoring. / Step 6 – before the surfaces go live: clear the test data, and make sure real content is in place. / Two groups sit outside the six steps: the fraud restriction items (DB-08, APP-18, APP-19), needed only once SOCO names the fraud roles, and the method comparison (ENG-26), which needs real traffic first. / Each surface then goes live if its checks pass (ENG-24). / New items added in v1.2 carry a proposed estimate in their Step. It stands unless the owner says otherwise in writing within 5 working days.
Which document wins | These five documents replace everything shared before. Delete or stop using all earlier packs, lists and drafts. / If two of the five say different things, this workbook wins, then the API contract, then the service design agreement, then the fraud policy, then the capture register. / Codes E, F, D and X refer to rows in the capture register. SD codes are rows in the service design agreement. AS codes are assumptions (the full list is on the Assumptions sheet). The Req ref column in the capture register (R1, R2 and so on) holds old labels: ignore it. No other document is needed.
Working days | Working days are counted from the day this pack is received, and the steps overlap: an item in a later step can start as soon as what it waits on is done. / If an item cannot be finished inside its step, say so in writing within 5 working days of receiving this workbook, with the number of working days you need. Silence is taken as agreement.
Questions | Write to Kala, quoting the item ID. You will get a written answer.
Rules that never change | The engine never writes to the platform database. Commission never affects what a shopper sees. The system flags fraud; a person decides. A buyer's identity from an incognito order is never shown to anyone else. The app shows the engine's list exactly as returned.
Status values | To build: not started. / In progress: being built. / Waiting: cannot go further until an item in 'Waits on' is done. / Built: the build is finished; the check has not been run yet. / Testing: the check in 'How to check it is done' is being run. / Failed: the check failed and is being fixed. / Passed: the check passed and the result is saved. The item is done. / Not needed: nothing to build in Wave 1A; the engine adapts (the item says how).
Sheets in this workbook | Build list: every item, with its dependencies. / Change register: what changed in each version, and when. / Waits on the other team: what each person needs from the other. / Settings: every value the engine and SOCO_BE use. / Definitions: the words used here. / Not in Wave 1A: what is left out, and what that means. / Assumptions: what was assumed, and what happens if it is wrong. / Kala: Kala's own items.
Documents to keep at hand
This workbook | The build list, dependencies, settings, definitions and your items. Start here, and work from it.
SOCO-REC-DS-017 API Contract v2.5 | The exact request, response and event formats between SOCO_BE and the engine.
SOCO-REC Service Design Agreement v1.6 | How the engine service is laid out.
SOCO Fraud and Abuse Policy v1.3 | The fraud levels, reviews, notices and appeals, in full. SOCO names the policy owner, reviewer and second approver on its first page.
SOCO-REC-DS-003a Capture Register (29 September 2026) | The field-by-field event list, for looking up one field.
Scope, basis and limitations | The model and method design in this workbook is Cristo Labs' deliverable. The technical design, meaning the interface between SOCO_BE and the recommendation service and the internal design of the service itself, sat with the SOCO engineering team. Those inputs were not received in a buildable form, so Cristo Labs has specified them as well, to keep the Wave 1A build on schedule. This is beyond the original scope of engagement and has been undertaken to protect the delivery date. /  / Where a fact about the SOCO application or database could not be confirmed by the team, it was either verified directly against the launch database or recorded as a stated assumption on the Assumptions sheet, together with its effect if it proves incorrect. Every decision, specification and assumption here is made in good faith, on the information available as at 22 September 2026, updated on 28 September 2026 from the platform team's APP-00 answers and the platform schema reference v4, and to the best of Cristo Labs' understanding of the SOCO platform as it stands today. /  / Cristo Labs is accountable for the quality and internal consistency of this specification. It is not accountable for outcomes arising from information not provided or not confirmed by the SOCO team, from assumptions that later prove incorrect, from implementation that departs from this specification, or from platform behaviour outside the scope described here. Where an assumption or a stated fact is found to be incorrect, the owner should notify Cristo Labs in writing and a revised version will be issued. /  / Wave 1A delivers a working, tested engine and the tracking it needs to learn. It does not warrant recommendation quality, which depends on real user traffic that does not yet exist.

=== SHEET: Definitions
Definitions
The words used in this workbook.
Term | Meaning
Surfaces | feed = the For You tab only. The Following, Trending and Local tabs keep their own rules and do not call the engine. product = product detail and cart. There are no other surfaces in Wave 1A.
Item types | post and product cards. item_id is the card shown (a post id on a post card, including a post that shows a product; a product id on a product card). post_id and product_id are kept alongside, so an event joins to the exact card shown and to its product.
Position | Counts from 1, in on-screen order, within each request, with no gaps. Each page is its own request. SOCO_BE shows engine lists unchanged, so the position on an event is the engine's position.
request_id | One per served list: UUID v4 on engine lists, req_… on the platform's fallback lists. It travels with the item: card → product detail → cart item (the first list that added it) → order. It is empty only on actions not reached from a list.
policy_id | The settings version plus the method used per slot, for example cfg3.interest-2.promoter-1. Fallback lists keep the platform's own policy_id (wave1a_v1 or prodrec_v1): any policy_id not starting with cfg is a fallback.
Seen, and a qualified view | Seen means at least 50% on screen. A qualified view means seen for at least 3 seconds.
Completed sale | order_status Delivered, past the product's return window, that never reached Return Requested or Returned. 'No return requested' means nobody asked to return it; it is not proof that a return was refused or a refund settled. Payed Off without Delivered is not a sale. The engine keeps the first time an order reached Delivered, from tracking_info, so a later state never erases that history. The engine never assumes order states arrive in order. Partial refunds are not modelled in Wave 1A.
Order status values | Pending, Accepted, Confirmed, Shipped, Payed Off, Delivered, Cancelled, Rejected, Return Requested, Returned. Read from order_status, with the history in tracking_info (APP-08). 
Events and where they are recorded | The app sends impressions, clicks and content feedback to SOCO_BE, and SOCO_BE records its own actions and orders, all in the platform database (postevents, orders, recommendationrequests). The engine reads them with its sync (ENG-04). Nothing is forwarded. The engine writes its own record of each list it serves.
Incognito | Purchase privacy only. Everything is recorded. Incognito orders count for the buyer's own recommendations and in anonymous totals, and a buyer's identity from an incognito order is never shown to anyone else. Fraud rules read them.
Fallback | SOCO_BE's existing ordering, shown whenever the engine is slow, down or off. Never visible to the user as an error. Counted separately from cold start, which is the engine answering normally for a user with little history.
Off, internal and live | Each surface is off (users see SOCO_BE's own ordering), internal (only the test accounts in the engine's settings see the engine's list, for checks before launch) or live (users see the engine's list). The go-live rule and safety switch in ENG-24 decide which. No person approves it.
Environments | The engine has dev, test and production, each with its own engine database; its test environment holds constructed platform-shaped data. There is no separate platform test environment: app checks run on test accounts in production with the surface in internal mode. 'Live' in this workbook always means a surface mode, never an environment.
Engine database | The engine writes only to its own database. It reads the platform database with a read-only login and never writes to it.
Model names | M1: interest profile. M2: finding candidate posts. M4: the ranking layer. M5: product ranker. M6: opportunity ordering (not shown). M8: promoter score. M9: fraud rules. Generic: used by every model or list.
Engine sync | The engine's job that copies postevents, orders and recommendationrequests from the platform database every 5 minutes by updated_at, and keeps the copies at least 365 days (ENG-04).
Serve log | rec_serve_log: one row per list request, written by SOCO_BE, with origin (engine, fallback or cache), outcome and elapsed time (APP-15). The fallback rate and speed are measured from it (ENG-24).
