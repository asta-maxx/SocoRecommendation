SOCO-REC-DS-017  API Contract  v2.5
SOCO Recommendation Intelligence Engine. Contract between SOCO_BE and the recommendation service. Issued by Kala (Cristo Labs), 29 September 2026. Status: frozen for build. Replaces v2.4 in full. v2.5 adapts the service to what the platform already has: lists are shown unchanged with a small serve log, order history comes from tracking_info, returns are read from Return Requested, blocks from followers, and the service keeps eligibility current itself. v2.3 was an internal draft and was not issued.
1. Status of this contract
This version replaces every earlier version of this contract, and SERVICE_CONTRACT v1.0, in full. Anything not stated here is not part of the contract.
Event (E), field (F), data model (D) and rule (X) codes refer to the SOCO-REC-DS-003a Capture Register, which is kept alongside this contract.
Where a fact still needs confirming from the app or the database, this contract states an assumption and is written to it. The assumptions are listed in Section 11, and each is marked [Assumed: AS-nn] where it applies.
If an assumption turns out to be wrong, the owner tells Cristo Labs in writing, and Cristo Labs issues the next version. The build does not stop while that happens.
Every change is listed, with its date, in the Wave 1A build list v1.3, sheet 'Change register'.

Contract
Identifiers
Every user, post, product and order id is the 24-character MongoDB ObjectId string. Prefixes such as usr_ or pst_ are never used on these ids. Event ids, request ids, session ids and checkout ids are opaque strings, stored exactly as written.
Server time
UTC, ISO 8601, with milliseconds.

Counts from 1, in the order shown on screen, with no gaps, within each request. Each page is its own request. A position of 0 is invalid. SOCO_BE shows engine lists unchanged, so the position on an event is the position the service returned.

request_id

request_id required
Present on every served-list record, and on every impression and click from a served list. On add-to-cart, purchase, social and feedback events it is null when the action did not come from a served list. Order status changes carry no request_id.
Authentication
POST /v1/recommendations carries a bearer token in the Authorization header (INGEST_TOKEN, kept as the name of the serving token). The service reads the platform database with its read-only login. [Assumed: AS-04]
Secrets
Tokens and database credentials are held only in server environment settings. Never in code, configuration files, the Flutter app, or any shared document.

Used only for the fallback ordering. It is never a model input.

4.3 Rules for SOCO_BE
Show the list exactly as returned: no filtering, re-ordering, trimming or added items, and no pull-to-refresh reshuffle of an engine list. The service applies every eligibility rule itself, re-checks the returned items when it builds each list, and returns exactly limit items unless fewer eligible items exist.
Serve log: for every list request, SOCO_BE writes one row to rec_serve_log with request_id, user_id, surface, page, origin (engine, fallback or cache), outcome (ok, timeout, error, off or skipped), elapsed_ms and the time. The operational fallback rate and the speed seen by SOCO_BE are measured from it (build list ENG-24).
Caching, if SOCO_BE caches lists: only for the same user_id, surface, page, limit and context_item_id, for no longer than 60 seconds, keeping the original request_id, and dropped at once when the user blocks someone or hides an item. No new E1 is written for a reused list, and the serve log records it with origin cache. A cache keyed only by surface or post is not allowed, because one user's list would be served to another and the method split would disappear.
Circuit breaker, if SOCO_BE uses one: after 5 failures in a row it stops calling the service and falls back, sending one test call every 30 seconds, and resumes when one succeeds. Each skipped call is logged with outcome skipped.
Timing: the service answers within 200 ms at p95, measured at SOCO_BE [Assumed: AS-07]. The hard timeout is 250 ms [Assumed: AS-07].
Exploration: on 5% of feed requests the service keeps the top 3 positions as ranked and shuffles the rest among eligible items. Those lists carry is_exploration true. Never on the product surface. The platform's own is_exploration flag on its lists (about 10% of discovery posts) is a different thing and is never set on an engine list.
4.4 Off and live
Each surface has a mode in the service configuration: off, internal or live. There is no shadow mode.
Live: SOCO_BE shows the returned items.
Off: the service returns 503, and SOCO_BE falls back.
Internal: only the test accounts listed in the service configuration get the returned items; every other request gets 503, and SOCO_BE falls back. Used for checks on production before launch.
At launch: a surface is set live only if its pre-launch checks pass, otherwise off until they do.
Safety switch: the service owner sets a surface to off at once if, in any one day, the fallback rate is above 10%, p95 is above 250 ms, or errors are above 2% of requests, or an acceptance check fails. It is switched back on when the cause is fixed. These are written rules. No approval is needed.
4.5 Fallback
On timeout, error or off, SOCO_BE serves its own ordering (the platform lists: wave1a_v1 for the feed, prodrec_v1 for product detail and cart), which must pass the same visibility rules the app already applies: blocked authors, hidden, private, deranked or removed posts and out-of-stock products are never shown. It keeps its own request_id (req_…) and policy_id, and writes its served-list record to recommendationrequests with origin fallback, as it does today. Any policy_id that does not start with cfg is a fallback list. Fallback lists produce every event, exactly like engine lists (X-03). The labels on the platform's own product rails follow build list APP-24.

5. How the method is chosen
Three slots carry two methods at launch. A user is assigned to a method per slot, the same way on every request, after every restart.

Rule
Contract
Identifier
The user_id of the person the list is for. Never a session id or device id.
Hash
SHA-256 of slot name and user_id joined by a colon, for example interest:65f1…. The first 8 hex characters, read as a number and taken mod 100, give the user's bucket (0 to 99). A bucket below the split value gets method two. Everyone else gets method one. The language's built-in hash is never used.
Independent slots
The slot name is part of the hash, so a user's method in one slot does not decide their method in another. The exploration slice is decided separately.
Configuration
Per slot: method one, method two, split (0 to 50) and default method, in the versioned configuration file. Read on each request or reloaded at least once a minute. Every change is logged with time, old value, new value and who made it.
Launch values
Split 50 in all three slots. Method one is the default.
Missing configuration
Every user gets the default method, the fault is logged, and the request still succeeds.
Missing score
The fallback ladder applies. The service still records the intended method and the fallback step used.
Both computed
The daily refresh computes both methods for every user. Serving reads the row for the assigned method.
Old scores
Time-windows scores written earlier without a method name are deleted and recomputed.

6.3 When client events are sent
Seen: at least 50% of the item is on screen, for every media type. A qualified view is seen and on screen for at least 3,000 ms (X-04).
Impression: one per item per list, sent when the item leaves the screen after being seen, or when the app goes to background, with dwell_ms for that first spell (at most 10 minutes). Not sent again if the item comes back into view in the same list. Unseen items are not sent; the service works out which items were seen from its own copy of impressions (X-05). An impression on the post page (surface post_detail) is a page visit: it is never a card impression or a qualified card view, and it is not counted as seen.
Click: a card-level tap that opens post or product detail. Taps on like, comment, share or save are E9, not E3 (E3).
request_id travels with the item: card → product detail → cart item → order. The cart item keeps the list that first added it (carts.ml). Quantity changes, removal and an order sent without context carry that list; a re-add from another list is credited to that list. Any action not reached from a served list carries null (X-07).
Undo is its own event: unlike, unsave, uncomment, unfollow and wishlist_remove. The original row is never deleted: it gets undone_at, and the undo row carries undo_of. A cancelled or rejected order's purchase row gets undone_at, but the order itself is the authority for its outcome (Section 6.4).
Incognito is purchase privacy only (Product Owner decision, 28 September 2026). Everything is recorded as normal: events, served lists and the order (isIncognitoMode true). The buyer's own activity shapes the buyer's own recommendations, and anonymous totals such as bought together include incognito orders. A buyer's identity from an incognito order is never shown to anyone else, by the service or by SOCO_BE: not in reasons, explanations or 'friends bought' displays. An order with no isIncognitoMode value is treated as incognito for any display that names buyers. Fraud rules read incognito orders (X-09).
6.4 Order values
Item
Contract
new_state
The status on each orders.tracking_info entry (build list APP-08), which is an order_status value: Pending, Accepted, Confirmed, Shipped, Payed Off, Delivered, Cancelled, Rejected, Return Requested or Returned. Processing and Out for Delivery are allowed by the platform but not written. The service stores and logs any other value rather than rejecting it.
Order states
The service does not assume states arrive in sequence. Payed Off can be reached without Delivered. The service takes the first time an order reached Delivered from tracking_info. The order (order_status and tracking_info) is the authority for an order's outcome. The purchase row's undone_at is a convenience, not the source. The status changes the service observes itself are a cross-check only.
reason_code
Optional. No Wave 1A scoring rule uses cancel reasons. The service stores whatever exists (reason_code, cancel_reason, cancel_reason_by_buyer, reject_reason_by_buyer) for investigation.
cancelled_by
Worked out, not stored: from the tracking_info entry, order_status and buyer_approval_status. Cancelled is by the buyer; Rejected with buyer_approval_status Rejected By Seller is by the seller; Rejected with buyer_approval_status Rejected is by the buyer.
Returns
No return event and no return fields. The existing Request return button moves order_status to Return Requested. The service treats any order that has reached Return Requested or Returned as returned. The exact stored value is held in the service's order-status map and checked on real rows (build list ENG-23 V8).
Scope decision: partial refunds are not modelled in Wave 1A.
How each model counts an order
M1 interest: +20 at order creation. The same 20 is taken off, once, when the order becomes Cancelled or Rejected, or a return is requested, or it becomes Returned.
M5 bought together: orders sharing a checkout_id, leaving out Cancelled and Rejected orders. Incognito orders count; no buyer is named.
M8 promoter: a completed sale is Delivered, past the product's return window, with no return requested and not Returned. An order still in progress counts on neither side.
M9 fraud: every order, including cancelled, rejected, returned and incognito orders, and every undone or own-post action.
7. How the service reads events (engine sync)
Source: the service reads postevents, orders, recommendationrequests and rec_serve_log from the platform database with its read-only login. For eligibility it also reads posts, users, businessregisters, products, productvariants, categories, follows and followers (blocks).
Batching from the app: unchanged. Flutter sends client events to SOCO_BE POST /events every 10 seconds, or when 20 have gathered, or when the app goes to background, whichever comes first. SOCO_BE stores them in postevents.
Reading: every 5 minutes, per collection, the rows with updated_at later than the last checkpoint, ordered by updated_at then _id, re-reading a 2-minute overlap. A row already held is updated, never skipped, so an undo, an order status change, a return request or new seen_ids arrive. The checkpoint is saved only after the batch is written.
Backfill: before the first incremental read, the service copies everything the platform still holds.
Store: ml_events (events and served lists) and ml_orders in the engine's own database, unique on the platform _id, keeping event_id, undo_of, undone_at and the original event time. Kept at least 365 days from the original event time, under the engine's own expiry; the platform's 90-day expiry never deletes them. [Assumed: AS-09]
Checks: an alert when any collection is more than 15 minutes behind; a daily reconciliation that compares ids and field values (undone_at, order_status, tracking_info, seen_ids), not just counts (build list ENG-04; the tracking_info comparison is added by ENG-29).
Eligibility data: posts, users, businessregisters, products and productvariants are re-read in full every 15 minutes, and only completed reads are used. Blocks, visibility and stock are also re-checked on the returned items when each list is built (build list ENG-08, ENG-27). A deleted account is purged only after a completed read, a direct lookup and a second completed read at least 24 hours later all confirm it is gone (ENG-28).
Platform obligations: the read-only login (DB-02) and the serve log (APP-15). updated_at on postevents, orders and recommendationrequests is reported built (APP-12) and checked by the reconciliation.
POST /v1/events, INGEST_TOKEN on events and the queued forwarding in v2.2 are retired.
8. Other endpoints
8.1 GET /health
Reports whether both database connections work: the platform database (read-only) and the engine database. Returns 200 when both work and 503 otherwise (SD-28). The path is [Assumed: AS-05].
8.2 Fraud case API
Used only by the admin panel, for the review screen. It carries ADMIN_TOKEN, not the serving token, plus X-Reviewer-Id and X-Reviewer-Role (owner, reviewer or second_approver) on every call. The service records both on the case, returns 403 for an action the role may not take or a second approval by the person who recorded the outcome, and 409 with detail roles_not_set while SOCO has not named the roles.
Endpoint
What it does
GET /v1/fraud/cases
The queue: case_id, account_id, level, rules hit, opened_at, due_at, priority. Takes state, page and limit.
GET /v1/fraud/cases/{case_id}
The full evidence: each rule hit with its observed value and the threshold in force, the orders, posts and accounts involved, earlier strikes and account age.
POST /v1/fraud/cases/{case_id}/outcome
outcome (confirmed, false_alarm, unclear), fraud_code on confirmed, level_chosen and reason. Returns the suggested level and the level recorded.

approve (true or false) and reason. second_approver only, and only on suspension or removal.
POST /v1/fraud/cases/{case_id}/appeal
appeal_text, from the app through SOCO_BE.
POST /v1/fraud/cases/{case_id}/appeal-outcome
decision (upheld, reduced, overturned), level_after and reason. second_approver only.

11. Assumptions

AS-22
